## Findings

### MAJOR
- **docs/Expand33PctMeasured.md:57 (Gate E row, "Analysis before porting … best shipped comparator `ROC_2`, per-frame median ρ 0.389")** — Nothing in docs/measure_expand3_3pct.py produces `ROC_2`, 0.389 or "12 synthetic tick-rounded frames". The script's own docstring says it is "the only place a figure in the receipt … may come from", and the acceptance criteria require every number in the receipt to come from that script. This number has no run behind it in the repo, which is the "claim written before it was measured" defect CLAUDE.md warns about. The script also builds 9 frames, not 12, so even the frame count does not match.
  - Fix: Either delete the sentence or add a section (for example `E0`) to measure_expand3_3pct.py that builds the 12 tick-rounded frames, computes the per-frame Spearman ρ against the shipped comparators and prints `ROC_2`'s median. Then quote that output exactly.

### MINOR / NIT
- **MINOR — pandas_ta/trend/expand3_3pct.py:8,17** — `pct` is only checked for `> 0`. When `pct >= 100`, `dn_k = 1 - pct/100 <= 0`, so `l2*dn_k >= l1` can never hold for positive prices. The −1 leg goes silently dead while the column name (`EXPAND3_150.0`) and the docstring ("the minimum step between consecutive … lows") still promise it.
  - Fix: Change the guard to `pct = float(pct) if pct and 0 < pct < 100 else 3.0`, document the range in Args, and add a one-line test that `pct=100` falls back to the default (or raises).
- **MINOR — pandas_ta/trend/expand3_3pct.py:71-74 and tests/test_expand3_3pct.py:36-37,324** — "any other positive factor can only flip a comparison sitting within one ulp of the 3% step" was neither measured nor derived. Each side carries one or two roundings (`fl(fl(h2*c)*k)` vs `fl(h1*c)`), so a comparison up to about 2 ulps from the step can flip, not 1. §D shows only that 0 bars flipped on these frames.
  - Fix: Reword to "can only flip a comparison within a few ulps of the step; measured 0 flips on every frame (§D)" in the module and test docstrings.
- **MINOR — tests/test_expand3_3pct.py:22-33, docs/measure_expand3_3pct.py:194-197** — The `h1-lead`/`l1-lead` look-ahead mutants are live (1..45 bars) but no test catches them. I re-ran the 400-bar range-bound sweep: 0 of 399 offsets caught for both. Gate B therefore has a known blind spot for a plausible off-by-one on `h1`/`l1`, and it is only disclosed.
  - Fix: Add one deterministic test per leg. Build a frame where bar j's high lands inside `[high[j-3]*1.03, high[j-1]/1.03]` in one future and outside it in the other, and assert the mutant is caught at offset j while the real module is not. Do the mirror for lows.
- **MINOR — docs/IndicatorDictionary.md:341,517 (generated by docs/gen_indicator_dictionary.py:490-495)** — The dictionary tags `EXPAND3_3.0` as `CONST` and lists it under "— unregistered, file one". Readers are told to consult this dictionary before judging a column, and here it calls a firing column dead. The rebuttal exists only in the receipt. It follows the precedent of stl_spikiness and others, but it is still misleading.
  - Fix: Add an `expand3_3pct` entry to `DEAD_TASKS` in gen_indicator_dictionary.py ("none — probe-frame artifact; fires 9..50 of 1,500 on moving synthetic frames, docs/Expand33PctMeasured.md §C; real-data count owed") and regenerate.
- **NIT — docs/Expand33PctMeasured.md (Cost section, §Z)** — The quoted timings (4.5 ms / 13.2 ms) do not reproduce. The reviewer's §Z run gave 5.5/5.1 ms and 14.5/16.6 ms. Peak memory (5.9 / 23.6 MB) does reproduce.
  - Fix: Present the times as approximate and machine-dependent ("~5 ms / ~15 ms on this machine"), or quote a range from several runs.
- **NIT — pandas_ta/trend/__init__.py:17, pandas_ta/core.py:2583** — Not in alphabetical order. In `__init__.py` the import sits between `dtdb` and `dx`, and in core.py the accessor sits before `equal_highs_lows` ("eq" < "ex"). Category and README place it correctly.
  - Fix: Move the import after `equal_highs_lows` in trend/__init__.py, and move the core.py method after `equal_highs_lows`.
- **NIT — pandas_ta/trend/expand3_3pct.py:62** — "the two differ only on steps between 2.913% and 3%" is algebra (1/1.03 = 0.97087), not a measurement, and the bound is rounded.
  - Fix: Write "steps in [2.9126%, 3%), since 1/1.03 = 0.97087; measured 0..2 bars per frame (receipt §A2)".

## Summary

The port is mathematically correct and the wiring is complete. The formula matches the issue's Pine line and the "lows 3% lower" mirror. The scalar-loop oracle is bit-equal to the module on all 9 frames at both 1,500 and 400 bars. These all match the script output and test runs the reviewer re-ran: the counts in §A1, A2, A3, B, C, CT, D, W and W2, the 128 tests passing, the 1,623 passed / 8 skipped targeted run, the 51, 44, 51, 44, 96 mutant catches, CATEGORY_TOTAL 396 / trend 67, the README placement and counts, and the contract's 741 tagged / 46 `CONST`. One thing fails the receipt standard the repo enforces: the `ROC_2` ρ 0.389 "analysis before porting" figure has no measuring code anywhere in the repo, which is the exact defect CLAUDE.md calls dominant, so this is REVISE until it is deleted or measured. Smaller real gaps: no upper bound on `pct` (the low leg dies at ≥100), an unmeasured "one ulp" claim, two live look-ahead mutants nothing catches, and a misleading `CONST` dictionary row with no annotation.

Reviewer's stated limits: §B1 was not run at 1,500 bars (the ~7-minute section), so the 80, 83, 84, 85, 169 walk catches and the "0..3 of 1,499" weak-mutant figures are unchecked; B1 was checked only at 400 bars.
