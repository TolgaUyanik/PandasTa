## Review round 1

VERDICT: REVISE
FINDINGS:
  - severity: MAJOR
    location: docs/measure_a101_026.py:68-72 (propagates into docs/A101026Measured.md Gate C row + "MID-STREAM NaN" section, tests/test_a101_026.py module docstring, and docs/reviews/auto-2026-11-08-a101-026/01-A101-026.md)
    problem: The script computes `warmup = max(5,5)+5+3-2 = 11` and then `expected_max_fires = n - warmup = 1489`, treating `warmup` (which is actually `min_length`, the minimum series length needed for one valid output) as if it were the count of leading NaN bars. It is not: the first valid output sits at 0-indexed position `min_length - 1 = 10`, so there are only 10 leading NaNs, not 11 -- confirmed independently by the same script's own `first_valid_index=10` print, and by `docs/IndicatorDictionary.md`'s own "warm-up" column for `a101_026`, which correctly says `10`. Re-deriving by hand: `n - fires = 1500 - 1252 = 248` total NaNs; `248 - 10 = 238` real mid-stream NaNs, not the claimed 237. Every place this number is quoted was off by one, and 15.9% should read ~16.0% (238/1490).
    fix: Stop reusing `min_length` as "warmup" for the fire-count arithmetic; use `first_valid` (already computed via `out.notna().idxmax()`) as the leading-NaN count, `expected_max_fires = n - first_valid`, giving `mid_stream_nan = 238`. Re-run the script and correct every downstream quote.
SUMMARY: The arithmetic that actually matters -- the Gate A hand-derivation, the Gate B mutant reachability and leak counts, the scale-free numbers, the wiring, the signature precedent, the full-suite pass count -- all checked out exactly against independent recomputation, and that's the only reason this wasn't a flat rejection. But a `min_length`-vs-leading-NaN-count off-by-one slid into the one number this session was explicitly told to scrutinize hardest, and it echoed, uncorrected, through four separate files.
